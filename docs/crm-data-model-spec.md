# CRM Data Model Specification

This document freezes the first CRM database structure before backend CRUD work begins.

The first implementation will use Google Sheets, but the structure should also be easy to migrate later to PostgreSQL or another real database.

## 1. Contacts Table

Google Sheets tab name:

```text
Contacts
```

Each row represents one person or organization contact.

| Field | Type | Required | Default | Validation Rules | Notes |
| --- | --- | --- | --- | --- | --- |
| contact_id | string | Yes | Generated by backend | Must be unique. Recommended format: `con_` + timestamp/random ID. | Primary ID for this contact. |
| first_name | string | Yes | None | 1-80 characters. Letters, spaces, hyphens, and apostrophes allowed. | Main personal name field. |
| last_name | string | Optional | Empty | 0-80 characters. Letters, spaces, hyphens, and apostrophes allowed. | Optional because some contacts may provide only one name. |
| display_name | string | Optional | Generated from first and last name | 1-160 characters if provided. | Useful for messaging apps and AI summaries. |
| email | string | Optional | Empty | Must be valid email format if provided. Store lowercase. | Optional because many messaging leads may not have email. |
| phone | string | Optional | Empty | 7-20 digits after normalization. May include `+` at the start. | General phone number. |
| whatsapp_id | string | Optional | Empty | 5-80 characters. | Future WhatsApp identity. Can be phone number or platform ID. |
| telegram_id | string | Optional | Empty | 3-80 characters. | Future Telegram numeric/user ID. |
| telegram_username | string | Optional | Empty | 3-80 characters. No spaces. | Future Telegram username without `@`. |
| line_id | string | Optional | Empty | 3-120 characters. | Future Line user ID. |
| preferred_channel | enum | Optional | `unknown` | One of: `unknown`, `phone`, `email`, `whatsapp`, `telegram`, `line`, `in_person`. | Helps future agent choose how to contact them. |
| country | string | Optional | Empty | 0-80 characters. | Country of residence or origin. |
| city | string | Optional | Empty | 0-80 characters. | City or local area. |
| language | enum | Optional | `unknown` | One of: `unknown`, `english`, `hebrew`, `spanish`, `russian`, `french`, `arabic`, `other`. | Useful for routing and AI replies. |
| status | enum | Yes | `new` | See Status Lifecycle below. | Current CRM state. |
| source | enum | Yes | `manual` | See Source Lifecycle below. | Where the contact came from. |
| source_detail | string | Optional | Empty | 0-250 characters. | Example: event name, campaign name, group name. |
| interest | enum | Optional | `unknown` | One of: `unknown`, `community`, `events`, `housing`, `jobs`, `business`, `language`, `support`, `other`. | Why they contacted Gringo Community. |
| priority | enum | Optional | `normal` | One of: `low`, `normal`, `high`, `urgent`. | Helps sort follow-ups. |
| assigned_to | string | Optional | Empty | 0-120 characters. | Future staff/admin name or user ID. |
| next_follow_up_at | datetime | Optional | Empty | Must be valid ISO date/time if provided. | For reminders later. |
| last_contacted_at | datetime | Optional | Empty | Must be valid ISO date/time if provided. | Updated when a real interaction happens. |
| tags | string list | Optional | Empty | Comma-separated list. Each tag 1-40 characters. | In Google Sheets this is one cell, later a separate table. |
| ai_summary | string | Optional | Empty | 0-2000 characters. | Future AI-generated contact summary. |
| ai_next_action | string | Optional | Empty | 0-500 characters. | Future AI recommendation. |
| ai_opt_in | boolean | Yes | `false` | Must be `true` or `false`. | Whether AI automation can interact with this contact. |
| marketing_opt_in | boolean | Yes | `false` | Must be `true` or `false`. | Whether marketing messages are allowed. |
| data_consent | boolean | Yes | `false` | Must be `true` or `false`. | Whether the contact consented to storing data. |
| notes_count | number | Yes | `0` | Integer greater than or equal to 0. | Cached count for quick display. |
| history_count | number | Yes | `0` | Integer greater than or equal to 0. | Cached count for quick display. |
| created_at | datetime | Yes | Current date/time | ISO 8601 format. | Created by backend. |
| updated_at | datetime | Yes | Current date/time | ISO 8601 format. | Updated by backend. |
| archived_at | datetime | Optional | Empty | ISO 8601 format if provided. | Used instead of permanent delete. |

## 2. Contact Field Validation Rules

At least one of these must exist:

- email
- phone
- whatsapp_id
- telegram_id
- telegram_username
- line_id

Other validation rules:

- `contact_id` cannot change after creation.
- `status` must always be one of the approved statuses.
- `source` must always be one of the approved sources.
- `created_at` cannot change after creation.
- `updated_at` changes whenever the contact row changes.
- `archived_at` is empty unless the contact is archived.
- The backend should normalize email to lowercase.
- The backend should trim extra spaces from all text fields.
- The backend should normalize phone numbers where possible, but should not destroy the original value until phone parsing is reliable.

## 3. Status Lifecycle

Approved statuses:

| Status | Meaning |
| --- | --- |
| new | Contact was created but not reviewed yet. |
| reviewed | Contact was reviewed by an admin. |
| contacted | Someone contacted the person. |
| engaged | The person replied or showed meaningful interest. |
| follow_up | The person needs follow-up. |
| active_member | The person became an active community member. |
| inactive | The person is no longer active. |
| not_relevant | The contact is not relevant to the community. |
| archived | The contact is hidden from normal active lists. |

Recommended status flow:

```text
new
  -> reviewed
  -> contacted
  -> engaged
  -> follow_up
  -> active_member
  -> inactive
  -> archived
```

Allowed side paths:

```text
new -> not_relevant
reviewed -> not_relevant
contacted -> not_relevant
engaged -> inactive
follow_up -> inactive
inactive -> active_member
active_member -> inactive
any status -> archived
archived -> previous status only by admin action
```

Default status:

```text
new
```

## 4. Source Lifecycle

Approved sources:

| Source | Meaning |
| --- | --- |
| manual | Added manually by an admin. |
| website | Came from a website form. |
| whatsapp | Came from WhatsApp. |
| telegram | Came from Telegram. |
| line | Came from Line. |
| referral | Came from another person. |
| event | Came from a community event. |
| facebook | Came from Facebook. |
| instagram | Came from Instagram. |
| google | Came from Google search or Google profile. |
| partner | Came from a partner organization. |
| import | Imported from an existing list. |
| ai_agent | Created or enriched by an AI agent. |
| other | Does not fit another source. |

Default source:

```text
manual
```

Source lifecycle rules:

- `source` should describe the original acquisition channel.
- `source` should usually not change after creation.
- `source_detail` can be updated later.
- If a contact first arrives from Telegram and later uses WhatsApp, keep `source` as `telegram` and update channel fields.
- If imported from another system, use `source = import` and put import batch details in `source_detail`.

## 5. Contact History Model

Google Sheets tab name:

```text
ContactHistory
```

Each row represents one event that happened to a contact.

| Field | Type | Required | Default | Validation Rules | Notes |
| --- | --- | --- | --- | --- | --- |
| history_id | string | Yes | Generated by backend | Must be unique. Recommended format: `his_` + timestamp/random ID. | Primary ID for history event. |
| contact_id | string | Yes | None | Must match an existing contact. | Connects history to contact. |
| event_type | enum | Yes | None | See event types below. | What happened. |
| channel | enum | Optional | `system` | One of: `system`, `phone`, `email`, `whatsapp`, `telegram`, `line`, `in_person`, `website`, `ai_agent`. | Where it happened. |
| direction | enum | Optional | `none` | One of: `none`, `inbound`, `outbound`. | Useful for messages. |
| title | string | Optional | Empty | 0-160 characters. | Short human-readable label. |
| description | string | Optional | Empty | 0-2000 characters. | Details of the event. |
| old_value | string | Optional | Empty | 0-500 characters. | For status/source/field changes. |
| new_value | string | Optional | Empty | 0-500 characters. | For status/source/field changes. |
| actor_type | enum | Yes | `admin` | One of: `admin`, `system`, `ai_agent`, `contact`. | Who caused it. |
| actor_id | string | Optional | Empty | 0-120 characters. | Future user ID, agent ID, or platform ID. |
| external_message_id | string | Optional | Empty | 0-200 characters. | Future WhatsApp/Telegram/Line message ID. |
| created_at | datetime | Yes | Current date/time | ISO 8601 format. | Created by backend. |

Approved history event types:

```text
contact_created
contact_updated
status_changed
source_updated
note_added
message_received
message_sent
call_logged
meeting_logged
follow_up_scheduled
follow_up_completed
ai_summary_created
ai_next_action_created
contact_archived
contact_restored
```

## 6. Notes Model

Google Sheets tab name:

```text
ContactNotes
```

Each row represents one note attached to a contact.

| Field | Type | Required | Default | Validation Rules | Notes |
| --- | --- | --- | --- | --- | --- |
| note_id | string | Yes | Generated by backend | Must be unique. Recommended format: `note_` + timestamp/random ID. | Primary ID for note. |
| contact_id | string | Yes | None | Must match an existing contact. | Connects note to contact. |
| body | string | Yes | None | 1-5000 characters. | Main note text. |
| note_type | enum | Yes | `general` | One of: `general`, `follow_up`, `call`, `meeting`, `ai_summary`, `internal`. | Helps organize notes later. |
| visibility | enum | Yes | `internal` | One of: `internal`, `shared`. | For future member-facing features. |
| created_by_type | enum | Yes | `admin` | One of: `admin`, `system`, `ai_agent`. | Who created the note. |
| created_by_id | string | Optional | Empty | 0-120 characters. | Future user or agent ID. |
| created_at | datetime | Yes | Current date/time | ISO 8601 format. | Created by backend. |
| updated_at | datetime | Yes | Current date/time | ISO 8601 format. | Updated by backend. |
| archived_at | datetime | Optional | Empty | ISO 8601 format if provided. | Used instead of deleting notes. |

## 7. Future Compatibility With Telegram, WhatsApp, And Line

The Contacts table includes platform identity fields from the start:

- `whatsapp_id`
- `telegram_id`
- `telegram_username`
- `line_id`
- `preferred_channel`

The ContactHistory table includes:

- `channel`
- `direction`
- `external_message_id`

This allows future message syncing without changing the core contact table.

Future platform message records can later be stored in a separate `Messages` table:

```text
message_id
contact_id
platform
platform_user_id
external_message_id
direction
message_type
body
media_url
sent_at
received_at
created_at
```

This future table is not part of the first CRM CRUD milestone.

## 8. Future Compatibility With AI Agent

The Contacts table includes:

- `ai_summary`
- `ai_next_action`
- `ai_opt_in`

The ContactHistory table includes:

- `actor_type = ai_agent`
- `channel = ai_agent`
- `event_type = ai_summary_created`
- `event_type = ai_next_action_created`

The Notes table includes:

- `note_type = ai_summary`
- `created_by_type = ai_agent`

Future AI agent behavior should follow these rules:

- The AI agent should not contact a person unless `ai_opt_in = true`.
- AI-generated recommendations should be saved in `ai_next_action`.
- AI summaries should be saved in `ai_summary` and logged in ContactHistory.
- AI-created notes should use `note_type = ai_summary` or `note_type = internal`.
- Human admins should be able to review AI-created content before sending messages.
